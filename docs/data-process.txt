一、总体架构（四层流水线）
================================================================================
Raw  ->  Staging  ->  Core  ->  Marts  ->  Dashboard

每一层在进入下一层前都会做契约校验；校验失败即停止流水线（§7，不产出文件）。

  层         位置                     产出                作用
  ----       ----                     ----                ----
  Raw        data/raw/                9 个 CSV 副本      不可变源数据
                                      + raw_manifest.csv + SHA-256 溯源清单
  Staging    data/staging/            9 个 Parquet       类型化、源对齐；不做 join/聚合
  Core       data/processed/core/     8 个 Parquet       规范事实表+维度表；明确粒度/主键
  Marts      data/processed/marts/    5 个 Parquet       扁平、可直接用；派生指标在这里做
  Dashboard  app.py + dashboard/      Streamlit 应用     只读 marts，不重复派生

--------------------------------------------------------------------------------

二、做了哪些清洗、各自的作用
--------------------------------------------------------------------------------
前提说明：Olist 是公开的干净数据集，所以这里的"清洗"主体是
「类型规范化 + 契约校验 + 一处地理过滤 + 明确的缺失值策略」，
而不是大规模删除脏数据。

2.1  类型规范化（staging 层）
  · datetime：pd.to_datetime(errors="coerce") -> datetime64
      作用：之后才能算 delivery_days、按月重采样
  · string：astype("string") -> 可空字符串
      作用：缺失统一记为 <NA>，避免「空字符串 vs NaN」混用
  · category：astype("category")
      作用：低基数枚举列（order_status/payment_type/州）转分类，省内存+锁值域
  · int64/float64：astype(...)
      作用：明确数值类型（int 只用于无缺失的列）

2.2  契约校验（值域/范围/日期）
  · 枚举白名单：order_status 8 种、payment_type 5 种、
    review_score 1-5、27 个巴西州缩写
  · 数值范围：price / freight_value >= 0；邮编前缀 0-100000；经纬度合法
  · 日期范围：2015-01-01 .. 2021-01-01
    （上限放宽到 2021 是为容纳 order_items 里 4 条异常的 2020 发货日期，保留不删）
  · 任何违规 -> 流水线 STOP，不写出该文件

2.3  主键唯一性 + 行数守恒
  · 主键唯一+非空校验：orders / order_items / payments / customers / sellers / products
  · 两张表故意不设主键（是数据本身特性，不是错误）：
      - reviews：源数据 review_id 有 789 个 id 重复出现在 1,603 行
      - geolocation：存在重复的 (zip, lat, lng) 行，无自然键
  · 行数守恒：每一层行数必须等于上一层（清洗不悄悄增删行）

2.4  地理过滤（core 层 dim_geography —— 唯一真正的"删行"）
  · geolocation 原始约 100 万行里有 26 行坐标在巴西境外
  · staging 保留它们（源对齐）；core 用巴西边界框过滤
      lat ∈ [-33.75, 5.30]，lng ∈ [-74, -34]
  · 然后按邮编前缀聚合成质心：州/城市取众数、经纬度取均值、n_records 计数
      -> 得到 19,010 个邮编前缀

2.5  缺失值策略（明确、有据）
  · 未交付订单的交付/批准日期天然缺失 -> 保留为 NA（业务事实）
  · review 的评论标题/正文常为空 -> 保留 <NA>
  · products 有 610 个"孤儿"产品（无类别/名称/照片元数据）-> 保留 <NA>
  · 产品英文类别名缺失 -> 回退葡萄牙语 -> 再回退 "unknown"

2.6  确定性校验
  · 同一份 raw 输入读两次、序列化成 Parquet 后字节完全一致
      -> 证明可复现，任何队友重新跑都得到完全相同的结果

四、marts 里派生出的指标（只在 marts 做，core 禁止，§4.5）
--------------------------------------------------------------------------------
  时间字段：order_purchase_date / year / month / year_month /
            day_of_week / day_name / hour
  交付指标：delivery_days（交付-购买）、late_days（交付-预估）、
            is_on_time、is_late（仅已交付订单填值，其余 NaN）
  支付汇总：payment_value_total、payment_installments_max、
            payment_count、payment_type_primary（金额最大的支付方式）
  订单汇总：order_item_count、order_price_total、order_freight_total、
            order_value_total、distinct_categories、top_category

  关键规则：订单级金额是"先按 item 聚合到订单再算"，
  绝不从 item 粒度直接 sum，避免一个订单多件商品时重复计数。

  全国州表现    巴西地图                state_summary    lat/lng + n_orders(大小) + on_time_rate(颜色)
  全国州表现    州准时率排名            state_summary    on_time_rate

六、Dashboard 使用的 5 张表（详述）
--------------------------------------------------------------------------------
以下按「用途 / 粒度 / 关键字段 / dashboard 用法」逐一说明全部 5 张 mart。

  ① mart_order_dashboard —— 一行一个订单（99,441 行）
     用途：订单级"事实表"，把商品/评论/支付的聚合结果、时间字段、
           交付结果都摊平到一行，是 KPI 视图唯一需要的数据源。
     关键字段：
       · 订单身份/状态：order_id、customer_id、order_status
       · 时间戳：order_purchase_timestamp、order_delivered_customer_date、
                 order_estimated_delivery_date
       · 客户：customer_unique_id、customer_city、customer_state
       · 商品/金额聚合：order_item_count、order_price_total、
                 order_freight_total、order_value_total、
                 distinct_categories、top_category
       · 评论：review_score、review_creation_date、has_review
       · 支付：payment_value_total、payment_installments_max、
                 payment_count、payment_type_primary
       · 时间派生：order_purchase_date、year、month、year_month、
                 day_of_week、day_name、hour
       · 交付结果：delivery_days、late_days、is_on_time、is_late
     dashboard 用法：
       · KPI 分数卡（订单量、营收、客单价、复购率、准时率、
         平均交付天数、平均评分，按期间）
       · 侧边栏的时间粒度与起止期间，都由 order_purchase_timestamp 计算

  ② mart_order_items —— 一行一个 (订单, 商品)（112,650 行）
     用途：商品级明细，已预先关联类别/卖家/客户/评论/支付上下文，
           使类别视图和地理视图无需再 join。
     关键字段：
       · 商品身份：order_id、order_item_id、product_id、seller_id
       · 金额：price、freight_value、item_value（= price + freight）
       · 类别：product_category_name、product_category_name_english、
                 product_weight_g
       · 订单上下文：order_status、order_purchase_timestamp、
                 order_delivered_customer_date、order_estimated_delivery_date
       · 客户：customer_unique_id、customer_city、customer_state
       · 卖家：seller_city、seller_state
       · 评论/支付：review_score、payment_value_total、... payment_type_primary
       · 时间 + 交付：同上 + delivery_days、late_days、is_on_time、is_late
     dashboard 用法：
       · Top 20 类别表（营收、订单、客户、平均评分、平均交付、1-2 星占比）
       · 类别涨跌（与前一期的营收差）
       · 类别深度分析（营收趋势、订单量、评分分布、交付箱线图）
       · 买家地理（customer_state）与卖家地理（seller_state）

  ③ mart_state_summary —— 一行一个州（27 行）
     用途：全量州级质心坐标 + 交付质量聚合（在已交付订单上计算）。
     关键字段：
       · state、state_name
       · lat、lng（质心，供地图定位）
       · zip_prefix_count
       · n_orders、total_value、avg_delivery_days、on_time_rate
     dashboard 用法：
       · 巴西全境地图（气泡大小=订单量、颜色=准时率）
       · 州准时率排名条形图（最差在前）
       · 准时率 vs 平均交付天数散点（气泡=订单量）

  ④ mart_category_daily —— 一行一个 (日期, 英文类别)（18,990 行）
     用途：每个类别每天的可加性计数，支撑天粒度时间序列。
     关键字段：
       · n_orders、items_sold、revenue
       · avg_price、avg_freight
       · n_delivered、n_on_time
       · n_reviews、sum_review_score、n_1_2_star
       · n_customers
     dashboard 用法：
       · Top 6 类别营收对比折线（多类别同屏比较）
       · 类别 × 月份营收热力图（季节性全景）

  ⑤ mart_data_quality —— 一行一张物化表（12 行）
     用途：运维/元数据自检，不是业务数据。
     关键字段：layer、table、grain、rows、primary_key、pk_unique、status
     dashboard 用法：
       · 数据质量状态表（折叠面板）
       · 各表行数柱状图（对数刻度）
